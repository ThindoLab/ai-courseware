# 样例反馈

只记观感。新记录追加在该件「记录」最上面。  
状态（`未看` / `可用` / `待改` / `搁置`）由助手在综合分析后改，不用手改。

## 说明（每次做反馈必须先读）

1. **点背后有层。** 记录里往往只写一个点，后面多半藏着更深层的问题。先问「为什么这一点会烦」，不要就点改点。
2. **条目会打架、会重复。** 几条反馈可能互斥，也可能是同一诉求说了两遍。要往下找到一致的诉求，不要并列执行互相打架的改法。
3. **聚成一套独立方案。** 把记录收成互不排斥、彼此独立的优化项。一项解决一个诉求，项与项不互相拆台。
4. **先确认再改。** 方案须与用户对齐后才能动手。未确认不得改 HTML / 工艺文。
5. **对抗反思。** 实施时对照历史较好的写法：会不会把已经清楚的图解、安全红线、一屏结构改坏。宁可少改，不要把好的改差。
6. **版本对上号。** 每条记录第一行写 `版本：vN`。`samples/<slug>.html` 是当前版（页头有 `<meta name="aid-version">`）；历史冻结在 `samples/versions/<slug>/vN.html`，可打开 `/samples/versions/<slug>/vN.html`。综合分析必须按该条所属版本看 HTML，不要把旧版差评和新版优点糊成一个现状。新版已经变好的点，不要用旧版问题盖掉。
7. **好评也要拆。** 用户说「还不错 / 很完美」时，不一定点出好在哪。助手要打开该版 HTML，对照同库较差篇和上一版，写出可复用的好点（记在该条「可复用」里，必要时同步 `pi/memory/keep.md`）。同时用两三句话同步**下一次迭代项**：锁住什么、还不改什么、若动只动哪一类。未确认仍不得改 HTML。
8. **迭代四栏。** 进入分批重跑的篇，每轮在 [分析/_迭代.md](分析/_迭代.md) 记齐：**版本**（vN + 轮次）· **反馈**（对该版原话）· **检查**（对着该版 HTML 是否属实）· **优化**（改了哪条系统通则、跑没跑）。不得用旧版差评盖新版，不得只记「重跑了」不记检查。一轮怎么走、选篇、锁皮、模型失败，见 [分析/_迭代须知.md](分析/_迭代须知.md)。
